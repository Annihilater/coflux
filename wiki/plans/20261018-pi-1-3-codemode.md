## Record

### Requirement

The executor (`packages/executor`, hosted either by Coflux.app's main process or by the npm `cofluxd` host) runs every task on `@earendil-works/pi-coding-agent` **0.85.1** (released 2026-09-05). The current release is **1.3.0** (2026-10-15): fifteen releases later, including 1.0. Staying behind means missing provider fixes, newer models in the settings picker, and the features pi has added since — of which one, codemode, fits the executor's workload directly.

When this is done:

1. The executor, in both hosts, runs on pi 1.3.0. Nothing about the executor's boundaries changes: same closed resource loader, same in-memory credentials and settings, same path guard, same transcript. The executor's own pi additionally runs with pi's install telemetry and provider attribution headers off.
2. Every run, read-only or write, has the full tool set: `read`, `edit`, `write`, `grep`, `find`, `ls` and the executor's own sandboxed `bash`. Until now `bash` was never registered: pi drops any custom tool its `tools` allowlist does not name. So the executor had no shell, could not run a test or a build, and the Seatbelt profile that wraps `bash` had never run on a real machine — although the coflux SKILL has promised all of that since the executor shipped. Read-only mode is enforced by the guard (`write`/`edit` refused) and by the Seatbelt profile (`bash` cannot write the workspace), not by hiding tools.
3. The executor's model can call a `codemode` tool: one JavaScript script, run by pi in a QuickJS sandbox, that calls the executor's own tools — several in parallel, filtering large outputs before the model sees them. This is exactly the executor's work: run a test suite and return only the failures, read or edit many files in one step, run a search that would otherwise take many tool calls. The seven ordinary tools stay available directly; the model scripts only when it pays.
4. Everything a script does goes through the same guard and sandbox as a direct call: a script cannot write outside the workspace, cannot write at all in read-only mode, and its writes still appear in the run's changed-files list. pi's own temp files for a script (overflowing output, images) land in the task's scratch directory, which is deleted with the task.
5. The run card shows a script step as one row labelled with the script's first meaningful line; the calls the script made appear as their own rows, as direct calls do today.

The calling agent sees no difference in the CLI: its inputs remain the prompt and the read/write mode only (product conclusion 3 of `wiki/plans/20260912-executor-engine.md`). There is no switch for codemode.

### Decisions & tradeoffs

- **D1 Pin exactly 1.3.0, in both manifests, in one change.** `packages/executor/package.json` and `packages/cli/package.json` both pin `"@earendil-works/pi-coding-agent": "1.3.0"` — an exact version, no range. Rejected: a caret range — the executor's isolation depends on pi internals (`getAgentDir()` fallback, config-value parsing, loader defaults) that a minor release can change unseen. Rejected: bumping only `packages/executor` — `cofluxd` vendors the executor's build at prepack and keeps pi external, so its own pi pin is the pi the daemon host actually loads; two different pins would run executor code against an untested pi. Based on: `packages/cli/package.json:23` (`--external:@earendil-works/pi-coding-agent`), `packages/cli/package.json:44`, `packages/executor/package.json:45`.

- **D2 The upgrade itself is behaviour-neutral.** Milestone 1 changes the version and turns telemetry off (D3) — nothing else. The closed loader, credential store, settings, bash backend, guard and transcript stay as they are. Based on: a copy of `packages/executor` type-checked against 1.3.0 outside the repo — `tsc -p tsconfig.build.json` and `tsc -p tsconfig.json` (with tests) both pass with no code change; the breaking changes listed between 0.85.1 and 1.3.0 (`shouldStopAfterTurn` removed, `SessionManager` canonical for history, `TurnEndEvent`, `Context`→`TranscriptContext` for custom stream providers, `user_bash` fail-closed, `azure-openai-responses`→`azure`, the `before_agent_start` union) touch nothing the executor uses; the input schemas of `read`/`edit`/`write`/`grep`/`find`/`ls` are identical in both versions (so `guard.ts` `PATH_FIELDS` still matches); the session events `transcript.ts` reads (`message_start`/`message_update`/`message_end`, `tool_execution_start`/`tool_execution_end` with `toolCallId`, `toolName`, `args`, `result`, `isError`) have the same shape in `pi-agent-core` 1.3.0; built-in MCP, codemode and tool_search are not loaded by SDK sessions and `noExtensions: true` disables them regardless (pi 1.3.0 `docs/sdk.md`, "codemode-mcp").

- **D3 The executor's pi runs with telemetry off.** pi's `enableInstallTelemetry` defaults to `true` and controls an install/update ping and provider attribution headers (OpenRouter, NVIDIA NIM, Cloudflare); `PI_TELEMETRY=0` overrides it. In SDK use only the attribution headers apply — the install ping is CLI-only — and they are added by `createAgentSession`'s request builder, which re-reads `PI_TELEMETRY` on every request, so the runner is where the switch takes effect. `runtime.ts` sets it too although its `ModelRuntime`/`completeSimple` never consult the flag in 1.3.0: it costs one line and covers a future pi that does `(revised on plan audit)`. Rejected: leaving pi's default — the executor's pi shares nothing with a pi the user installed (runner.ts header, point 5), and a third party learning which tool the user's key is driving is not something the user asked for. Based on: pi `docs/settings.md` ("Updates, telemetry, and warnings") and `docs/environment-variables.md` (`PI_TELEMETRY`) — present unchanged in 0.85.1 and 1.3.0; `packages/executor/src/runner.ts:239-240` and `packages/executor/src/runtime.ts:140-141` already set pi's environment before import; pi 1.3.0 `dist/core/telemetry.js` (`isInstallTelemetryEnabled(settingsManager, process.env.PI_TELEMETRY)`), `dist/core/provider-attribution.js` via `dist/core/sdk.js` `buildRequestOptions`, the install ping only in `dist/modes/interactive/interactive-mode.js` (audit).

- **D4 Codemode is enabled as an inline extension of the closed loader, in both modes, with `mode: "on"` and `models: false`.** The runner adds pi's `createCodemodeExtension({ mode: "on", models: false })` (exported from the package root in 1.3.0) to the closed `DefaultResourceLoader`'s `extensionFactories`, beside the guard extension, and activates it by naming `codemode` in `createAgentSession`'s `tools` list in read-only and write runs alike. pi registers codemode inactive, and with a plain `tools` list that list is pi's allowlist: `defaultTools: ["+codemode"]` is then ignored, and the session has no `setActiveTools` `(revised on plan audit)`. The loader's `no*` flags stay `true`. Accepted cost: in mode `on` pi appends a calling note to every declared tool's description and inlines tool declarations into the `codemode` description up to `inlineBudget` (default about 3000 estimated tokens), so every request carries roughly 3k more prompt tokens — expected, not a regression `(revised on plan audit)`. Rejected: mode `only` — it hides the seven tools behind scripts, so even a single `read` costs a script, which is slower and costlier with the fast models the executor is usually configured with. Rejected: loading codemode as pi's built-in extension — that path is discovery, which `noExtensions: true` exists to keep shut. Rejected: `models` left on — scripts could then run classifier and image models with the user's key, paid work nobody asked the executor for. Rejected: a per-run switch — the executor's inputs are the prompt and the mode only. Based on: pi 1.3.0 `dist/extensions/codemode/index.d.ts` (`CodemodeExtensionOptions { mode, inlineBudget, models }`, "`codemode` is registered inactive. Activate it with `--tools`, the `defaultTools` setting, or `setActiveTools()`"), `dist/index.d.ts` (exports `createCodemodeExtension`), `docs/codemode.md` ("mode", "Models"); `dist/core/sdk.js:151-157` (a plain `tools` list is the allowlist); `dist/extensions/codemode/tool.js:215-219` (`prepareCodemodeLoadout`); the audit's probe (codemode active and callable with all five `no*` flags `true`); the Discussion log.

- **D5 Containment is the existing guard and sandbox; nothing codemode-specific is added to them.** A script runs in QuickJS with no Node APIs, file system, network or timers; it reaches the outside only through `tools.<name>()` (and `models`, off per D4). pi routes every such call through argument validation and the `tool_call` / `tool_result` handlers exactly like a model-issued call, and emits `tool_execution_start`/`update`/`end` for it with `parentToolCallId` set and a `toolCallId` of `<parent id>/<n>`. So `guard.ts` (path check, read-only refusal, changed-files recording) and the sandboxed bash custom tool apply to every call a script makes, and `transcript.ts` already records each one as its own row. The `codemode` call itself carries no path and passes the guard untouched. Rejected: a codemode-aware guard branch — it would duplicate pi's pipeline and could drift from it. Based on: pi 1.3.0 `docs/codemode.md` ("Scripts"), `docs/extensions.md` (nested calls, `ctx.executeTool`), `docs/mcp.md` ("Every MCP call passes through Pi's tool pipeline … Calls made from codemode scripts carry the codemode call ID as `parentToolCallId`").

- **D6 The runner process's own temp directory is the task's scratch directory.** pi writes some codemode artefacts to temp files from the runner process itself: a script's output beyond `max_output_tokens` ("the full text is written to a temp file") and every `image()` block ("each image is also saved to a temp file"). The runner is **outside** Seatbelt, so today those would land in the system temp directory, outside the task's boundary and outliving the task. Pointing the runner's own `TMPDIR` at the scratch dir (set before pi is imported) keeps them inside the directory `manager.ts` deletes when the task ends; bash's truncated-output spill (`pi-bash-*.log`) moves with it. Accepted consequence: when pi tells the model where a spilled file is, the path is now in the scratch dir, outside the workspace, so the guard refuses a follow-up `read` of it — as it already did while the file sat in the system temp. That is not a guard bug `(revised on plan audit)`. Rejected: leaving it — model-controlled content written outside the task's scratch dir with no cleanup. Based on: pi 1.3.0 `docs/codemode.md`; `packages/executor/src/runner.ts:139` sets `TMPDIR` only for tool children; `packages/executor/src/manager.ts` creates the scratch dir with `mkdtempSync` and removes it at task end (`cleanScratch`).

- **D7 A script step on the card is one row labelled by the script's first meaningful line.** The card renders a tool row as `${tool} ${argument}` (`apps/desktop/src/renderer/components/workbench/executor-run-card.tsx:772,785`), and `transcript.ts` `salientArgument` falls back to the JSON of the arguments for unknown tools, which for codemode would be `{"code":"…the whole script…"}`. `salientArgument` gains a `codemode` case: the first line of `code` that is neither blank nor the `// @options:` line, trimmed. No renderer change. Rejected: a nested/indented UI for script children — the children already appear as ordinary rows, and the card is read-only and transient.

- **D8 MCP, tool_search, Pi Durable and virtual models are not adopted.** MCP: local (stdio) MCP servers are processes pi would start from the runner, which has network and is not sandboxed — a breach of the executor's containment — and their configuration would come either from the user's `~/.pi` (the state the executor deliberately never reads) or from the workspace's `.pi/mcp.json` (the vector the closed loader exists to block); the calling agent has MCP of its own. tool_search: exists for large tool sets; the executor has seven. Pi Durable: built for long-lived, multi-party agents whose work outlives processes; the executor is one-shot and single-caller, and its result matters only while the caller waits (`wiki/plans/20260912-executor-engine.md:42`, `:75`; `packages/executor/src/jobs.ts:21`). Virtual models: route across providers; the executor uses one account-level model. Based on: the Discussion log.

- **D10 The sandboxed bash backend follows pi's `exec` contract: `timeout` is in seconds, a timeout rejects with `timeout:<N>`, an abort rejects with `aborted`** `(revised during verification)`. Rejected: keeping the millisecond reading — it kills any command the model gives a timeout within N ms, which surfaced as "Command terminated without an exit code" in the first real read-only run. The bug predates this plan and stayed hidden only because `bash` was never registered (D9). Based on: pi 1.3.0 `dist/core/tools/bash.js:16-26` (`resolveTimeoutMs`: `timeout * 1000`), `:259-283` (`ops.exec(…, { timeout })` with the raw parameter; `timeout:`/`aborted` rejections mapped to readable statuses; `exitCode === null` → "Command terminated without an exit code"); the same contract in 0.85.1 `bash.js:14-24`; `packages/executor/src/runner.ts` `sandboxedBashOperations` (`setTimeout(…, options.timeout)`).

- **D9 Every run gets the full tool set; read-only is enforced by the guard and the sandbox, not by hiding tools** `(revised on plan audit)`. Read-only and write runs alike register `read`, `edit`, `write`, `grep`, `find`, `ls` and the runner's sandboxed `bash` (plus `codemode`, D4). pi's `tools` option is an allowlist that also filters `customTools`, and the executor's lists never named `bash`, so its shell was never registered: no test or build could run, and the Seatbelt profile wrapping `bash` never ran on a real machine. Naming `bash` registers the runner's definition, not pi's, because a custom tool overwrites the built-in of the same name. In read-only runs `write` and `edit` are visible but always refused by `guard.ts` (`MUTATING_TOOLS`, refused before any path check), and under the read-only profile `bash` cannot write the workspace. Accepted cost: a read-only model may try a write once and read the guard's refusal. Rejected: separate tool lists per mode — the user: "Do not disable any tools, enable all tools"; per-mode lists are also how `bash` went missing unnoticed. Excluded despite that instruction: pi's built-in `powershell`. Its default backend runs commands through local shell operations in the runner process, outside Seatbelt and with network, so it would be a second, unsandboxed shell; it is also Windows' shell and needs `pwsh` on macOS. Based on: pi 0.85.1 `dist/core/agent-session.js:2110-2118` and 1.3.0 `:2846-2896` (the allowlist filters custom tools; custom tools overwrite built-ins of the same name); 1.3.0 `dist/core/tools/powershell.js` (`createLocalPowerShellOperations`); `packages/executor/src/runner.ts:382`; `git log -S` puts the lists' origin at `f63e925c`; Discussion log entry 9.

#### T3a · The sandboxed bash honours pi's timeout and abort contract

- Where: `packages/executor/src/runner.ts` — `function sandboxedBashOperations(start: ExecutorRunnerStart)`, its `exec` (the `options.timeout` timer, `onAbort`, and the returned promise).
- Change: treat `options.timeout` as **seconds**, which is what pi passes (`ops.exec(command, cwd, { onData, signal, timeout, env })` hands over the tool's own `timeout` parameter unconverted; pi's own backend multiplies by 1000). Report a timeout and an abort the way pi's backend does.
- After: a command with `timeout: N` is killed by process group only after N seconds, never after N milliseconds. When our timer killed it, the promise rejects with `new Error(\`timeout:${options.timeout}\`)`, so pi shows "Command timed out after N seconds". When the abort signal killed it, the promise rejects with `new Error("aborted")`, so pi shows "Command aborted". A shell killed by any other signal resolves with `exitCode` 128 + the signal number (pi's convention), not `null`. Everything else stays as it is: the group is still recorded in `liveGroups` and removed on close, `SIGKILL` on timeout and `SIGTERM` on abort are unchanged, and the command is still passed verbatim through `sandboxArgv` (D10).
- Don't: drop the timeout or cap it yourself; the run-level wall-clock cap is the host's (D10).

### Landmines

- `~/.coflux/executor-settings.json` holds the user's provider key in plaintext. Never print, copy or log it.
- Do not start, stop or modify the installed Coflux.app, its daemon, or anything under `~/.coflux`; nothing in this plan needs a running app.
- This session's shell guard refuses commands that put a variable where a path or option could stand, and compound git write commands; use literal paths and one git command per call.
- `transcript.ts` and `guard.ts` read pi's events and tool inputs through loose types on purpose, so the compiler will not catch a shape mismatch there. Do not "fix" that by importing pi types into them.
- pi's `tools` option is an allowlist that also filters `customTools`: a custom tool it does not name is dropped from the registry without a warning, and no codemode script can reach it. pi's docs recommend `defaultTools`, but that advice assumes there is no `tools` list.

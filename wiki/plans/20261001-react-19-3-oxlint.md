## Requirement

The desktop renderer (`apps/desktop/src/renderer`, ~144 `.ts`/`.tsx` files, ~32k lines) is the only React code in the repository. It builds with React 19.2.7 and `babel-plugin-react-compiler@1.0.0`, but:

1. React 19.3.0 shipped on 2026-09-09 with `<ViewTransition>` and Fragment refs promoted to stable, Transitions rendered independently instead of entangled, and fixes for `useDeferredValue` getting stuck, `useEffectEvent` reading stale values in `memo` components, and several `<Activity>` issues. Its release notes list no breaking changes. The renderer is still on 19.2.7.
2. The repository has no linter at all. When a component breaks the Rules of React, the React Compiler silently skips optimizing it: nothing errors, the component is just slower. Nobody can notice this while using the product.

Once this plan is done:

- `react`, `react-dom`, `@types/react` and `@types/react-dom` resolve to 19.3.x in `apps/desktop`. Type-level access to the 19.3 APIs (`ViewTransition`, a `ref` on `Fragment`) compiles.
- `pnpm -C apps/desktop lint` runs oxlint over the renderer with the hooks rules and oxlint's React Compiler rules enabled. It exits 0 on this branch.
- CI's desktop step runs that lint, so a later change that breaks a hooks rule or a compiler rule fails CI.
- The app behaves exactly as before. This is a dependency and tooling change, not a product change.

## Decisions & tradeoffs

- **The linter is oxlint, using only its native React rules (revised on plan audit).** Enable exactly these 14 rules, all at `error`:
  - `react/rules-of-hooks` and `react/exhaustive-deps`;
  - the 12 React Compiler rules oxlint places in its `correctness` category: `react/error-boundaries`, `react/globals`, `react/immutability`, `react/incompatible-library`, `react/preserve-manual-memoization`, `react/purity`, `react/refs`, `react/set-state-in-effect`, `react/set-state-in-render`, `react/static-components`, `react/use-memo`, `react/void-use-memo`. They are lint-only analysis on Oxc's port of the React Compiler.

  Do not use the old nursery rule `react/react-compiler`. oxlint 1.79 split it into these per-category rules (oxc commit `8c4552df`, blog `oxc.rs/blog/2026-08-18-react-compiler-support`), and 1.86.0 no longer has it; an unknown rule name is a hard config error. Rejected: ESLint + `eslint-plugin-react-hooks@7`. It has the official, Babel-identical compiler diagnostics, but it is slower, adds ESLint plus a TS parser as a second toolchain, and diverges from the owner's oxlint baseline. Rejected: oxlint `jsPlugins` loading `eslint-plugin-react-hooks`. JS plugins are alpha, and the compiler rule would still run in JS, so the speed advantage would be lost. Based on: the user raised ESLint performance after the first direction and asked for the current best option. The oxc docs (rules `react/rules-of-hooks`, `react/exhaustive-deps`, `react/react-compiler`; `jsPlugins` marked alpha) were checked on 2026-10-01; oxlint is at 1.86.0 on npm. The choice was made under the owner's standing rule that purely technical choices go to the fastest and most elegant option.
- **Only those 14 rules run (revised on plan audit).** The config sets `"plugins": ["react"]`. Setting `plugins` overwrites oxlint's default plugin set (`eslint`, `typescript`, `unicorn`, `oxc`); react is not on by default. The config also sets `"categories": {"correctness": "off"}` and names the 14 rules one by one under `rules`. Rejected: `"categories": {"correctness": "error"}`, which is what the oxc blog suggests, because it would also enable every other react correctness rule (`jsx-key`, `no-children-prop`, …). Also rejected: keeping the default plugins and categories, which would surface unrelated findings. Widening the rule set is future work.
- **`react/unsupported-syntax` and `react/hooks` stay off (revised on plan audit).** `react/unsupported-syntax` (restriction category) reports components the compiler skips because of syntax it does not support. Those bailouts are specific to Oxc's port and do not reliably match what the Babel compiler used by the build does; only actual Rules of React violations gate CI. `react/hooks` (suspicious category) is the compiler's own version of rules-of-hooks and overlaps `react/rules-of-hooks`.
- **Lint scope is `apps/desktop/src/renderer` only.** Main and preload contain no React code.
- **The oxlint version is pinned in `pnpm-lock.yaml`** by declaring it as a devDependency of `apps/desktop`, the same way every other desktop tool is declared. A nursery rule can change behaviour between releases, so oxlint upgrades must be deliberate, never implicit. Rejected: `npx oxlint` / `pnpm dlx`, because they are unpinned.
- **CI gate**: the lint runs inside the existing desktop step at `.github/workflows/ci.yml:164`, as `pnpm -C apps/desktop typecheck && pnpm -C apps/desktop lint && pnpm -C apps/desktop test && pnpm -C apps/desktop build`. Do not add a separate job. Rationale: AGENTS.md "Test harness" automates only breaks that stay invisible while using the product, and compiler bailouts are exactly that kind of break.
- **Existing violations are cleared, not baselined.** Fix a violation when the fix keeps behaviour. When a fix is not worth it, or the rule is wrong, add a per-line `oxlint-disable-next-line <rule> -- <reason>` comment with a concrete reason. Rejected: a file-level or directory-level disable, and downgrading any of the 14 rules to `warn`, because either would let the gate pass while violations remain.
- **React 19.3 upgrade**: `react`/`react-dom` go to `^19.3.0`. `@types/react`/`@types/react-dom` go to their 19.3 releases (`@types/react` latest was 19.3.0 on 2026-10-01). `babel-plugin-react-compiler` stays at `^1.0.0`, which is still npm `latest` on 2026-10-01, and its config at `apps/desktop/electron.vite.config.ts:89-92` stays as it is. Based on: only `apps/desktop/package.json` declares `react`; no other package in `apps/`, `packages/` or `integrations/` does.
- **Non-goals, deliberately excluded**:
  - Do not remove the existing `useMemo`/`useCallback` calls (22 and 11). They are redundant under the compiler but harmless, and removing them could change effect-dependency semantics.
  - Do not enable StrictMode. It is deliberately off, per `apps/desktop/src/renderer/main.tsx:103-104` and plan 011.
  - Do not adopt `<ViewTransition>`, `<Activity>` or Fragment refs anywhere. That is product work for a separate plan.
  - Do not upgrade `vite`, `@vitejs/plugin-react` or `electron-vite`.
  - Do not add `oxfmt`.
- **Left to the executor**: the exact oxlint version (`>=1.86.0`; current latest is fine); the config file format (`.oxlintrc.json` is preferred, because `oxlint.config.ts` needs Node 22.18+) and its location inside `apps/desktop`, which is where `pnpm -C apps/desktop lint` looks for config; how the lint script targets the renderer; and how each existing violation is resolved within the rules above.

## Direction

### Milestone 1: React 19.3 resolves and everything still builds

`apps/desktop` resolves `react`, `react-dom`, `@types/react` and `@types/react-dom` at 19.3.x, and the lockfile is updated. A behaviour change that the 19.3 release notes mention (for example, Transitions no longer entangled) is not fixed pre-emptively. Only failures that the gates actually surface are fixed.
Validation: `pnpm -C apps/desktop typecheck && pnpm -C apps/desktop test && pnpm -C apps/desktop build` -> exit 0. `node -p "require('./apps/desktop/node_modules/react/package.json').version"` prints `19.3.x`.

### Milestone 2: `pnpm -C apps/desktop lint` exists, enforces the 14 rules, and is clean

Oxlint is a pinned devDependency of `apps/desktop`. A config enables exactly the 14 rules from Decisions & tradeoffs and nothing else. The `lint` script runs it over `src/renderer`. Before resolving anything, record the violation count per rule from the first run; the STOP threshold below applies to it. Every existing violation is fixed or disabled per line with a reason. The CI desktop step includes the lint.
Validation:
- `pnpm -C apps/desktop lint` -> exit 0.
- `pnpm -C apps/desktop exec oxlint --print-config` (run from the lint's config location) shows exactly the 14 rules on and `correctness` off.
- Three temporary probes in a renderer component, each on its own, make the lint exit non-zero:
  - a conditional `useState` call (`react/rules-of-hooks`);
  - `useEffect(() => { console.log(prop) }, [])` that reads a prop (`react/exhaustive-deps`);
  - `const r = Math.random()` at the top level of a component (`react/purity`).

  Revert all three afterwards.
- `pnpm -C apps/desktop typecheck && pnpm -C apps/desktop test && pnpm -C apps/desktop build` -> exit 0.

Dependency: Milestone 2 runs after Milestone 1. Both touch `apps/desktop/package.json` and `pnpm-lock.yaml`, and violations are judged against the 19.3 code. Execute as one package; do not fan out.

## Landmines

- **A misspelled rule fails loudly; a missing one does not.** In oxlint 1.86.0 an unknown rule name makes config parsing fail with a non-zero exit, so a typo shows up immediately. The quiet failure is a rule left out, or the react plugin not enabled at all. The three probes and `--print-config` in Milestone 2 cover that. Old docs and caches (including context7) still describe the removed `react/react-compiler` rule and its `reportAllBailouts` option; ignore them.
- **Imperative-resource code is where `react/set-state-in-effect` and `react/refs` will report most** (xterm instances, WS consumers, terminal panes). Expect most of the violations there, and apply the next landmine to every one.
- **Code changes made to satisfy a lint rule are behaviour changes in a hand-accepted app.** `exhaustive-deps` "fixes" in particular can turn a deliberately one-shot effect into one that re-runs. Example: terminal attach/detach and WS consumer registration are imperative resources; see the StrictMode rationale at `apps/desktop/src/renderer/main.tsx:103-104`. Do not add a dependency when adding it would change when an imperative effect runs. Disable that line with a reason instead. List every per-line disable in the final report so the reviewer can scan them.
- **A test pins the CI desktop command text (found at execution preflight).** `apps/desktop/test/config.test.ts:305-308` asserts that `.github/workflows/ci.yml` matches `typecheck && test && build` verbatim. Inserting the lint into that step breaks the test, so update its expectation to the new command in the same change. Do not weaken it into a looser match.
- **`pnpm -C apps/desktop pack` is captured by pnpm's built-in command.** It is not needed here; mentioned only so nobody uses it as a check.

## STOP conditions

- Any of the 14 rules does not exist in the installed oxlint, or cannot be enabled. Report this; do not fall back to ESLint or swap in other rules without a new decision.
- The 19.3 upgrade breaks typecheck, test or build in a way that needs changes outside the renderer, or needs behaviour changes beyond trivial typing fixes.
- Resolving the existing violations would need more than about 30 per-line disables, which would show that the rule set is too noisy for this codebase. Report the counts per rule from the first run instead of mass-disabling.
- A validation command fails twice after one reasonable fix.

## Maintenance notes

- The compiler rules analyse with Oxc's port of the compiler, while the build uses Babel's. A component that passes the lint is not guaranteed to be optimized by the build, and the reverse can also happen. Treat the lint as a strong signal, not proof.
- Upgrading oxlint can change nursery-rule results. Upgrade it on purpose, and expect to revisit the per-line disables.
- Possible follow-ups, each needing its own plan: widening oxlint to its `correctness` category; adopting `<ViewTransition>` for tab and sidebar transitions.
- Plan audit (fable, 2026-10-01) verified: per-line disable syntax `// oxlint-disable-next-line <rule> -- <reason>` (`crates/oxc_linter/src/disable_directives.rs` at `oxlint_v1.86.0`); every react peer range in `apps/desktop` accepts 19.3; `@types/react-dom@19.3.0` peers `@types/react ^19.3.0`, so they move together; the compiler config spans `electron.vite.config.ts:89-93`.
